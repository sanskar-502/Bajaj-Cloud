Why PolicyMind is Different

What sets this RAG apart from typical tutorial-level implementations

Architecture ☁️
Cloud-Native Integrated Embeddings
Most RAGs generate embeddings locally with sentence-transformers, creating a CPU bottleneck. PolicyMind delegates embedding to Pinecone's integrated embedding models — the vector DB itself generates embeddings at index time, eliminating a separate embedding service entirely.
Model: llama-text-embed-v2 · Zero local GPU/CPU cost · Automatic scaling
Explainability 🌿
Structured Logic Tree Reasoning
Typical RAGs return just an answer. PolicyMind generates a full AND/OR/CONDITIONAL logic tree via a second LLM call, showing exactly which clauses contribute to the answer and whether each condition is met — full explainability.
JSON-structured output via response_mime_type="application/json" · Pydantic-validated
Reliability 🛡️
Production-Grade Fault Tolerance
LLM APIs fail. PolicyMind wraps every LLM call in exponential-backoff retry logic (tenacity), uses fully async I/O to prevent thread blocking, and implements strict dependency injection for testability.
@retry(stop=3, wait=exponential) · AsyncOpenAI · generate_content_async
Versatility 📑
Multi-Format with OCR Fallback
Not just PDFs. PolicyMind processes PDF, DOCX, PPTX, and TXT files. For scanned/image-based PDFs, it automatically falls back to Tesseract OCR via pdf2image — extracting text from documents that break most RAG pipelines.
PyMuPDF → OCR fallback · pytesseract + pdf2image · Sentence-boundary chunking

Engineering Approaches & Design Decisions

Key technical choices that make the system efficient and maintainable

01
Sentence-Boundary Aware Chunking with Overlap
Instead of naive fixed-length splitting that breaks mid-sentence, the document processor uses NLTK sentence tokenization to split at natural sentence boundaries. Each chunk has configurable overlap (default 200 chars) to preserve cross-boundary context — critical for policy documents where clause meaning spans multiple sentences.
sent_tokenize(text) → overlap window → chunk_size=1000, overlap=200
02
Fully Async LLM I/O
All LLM calls use async clients (AsyncOpenAI, generate_content_async) so the FastAPI event loop is never blocked during high-latency AI calls — enabling concurrent request handling.
03
Dependency Injection Container
Services are wired via a @dataclass AppContainer built once at startup. This makes every component independently testable and avoids global state — a pattern used in production Python systems.
04
Abstract Provider Pattern
The LLMProvider ABC defines a contract for generate_response and generate_structured_response. Swapping from Gemini to OpenAI requires changing one env var — zero code changes.
05
Structured JSON Generation
Logic trees use native JSON modes: Gemini's response_mime_type="application/json" and OpenAI's response_format=json_object. Outputs are validated with Pydantic recursive models.
06
Exponential Backoff Retry
Every LLM call is wrapped with tenacity — 3 attempts with exponential wait (2s → 4s → 10s max). Gracefully handles rate limits and transient API failures without crashing.
07
Background Document Processing
File uploads return immediately with a document ID. The heavy extraction → chunking → embedding pipeline runs in a FastAPI BackgroundTask, keeping API response times under 200ms.
08
Self-Assessed Confidence Scoring
The LLM is prompted to evaluate its own answer confidence (0.0–1.0) based on evidence quality. This score is parsed from the response via regex and surfaced in the API — enabling downstream decision-making.
09
CI/CD with Static Analysis
GitHub Actions pipeline runs Ruff (linting), MyPy (static typing), and Pytest on every push. Type annotations are enforced across the entire codebase for production reliability.
